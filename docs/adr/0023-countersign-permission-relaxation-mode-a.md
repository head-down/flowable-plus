# ADR-0023: 模式A加签/减签权限放宽为"会签发起人 OR 当前节点活跃审批人"

**日期**: 2026-08-08
**状态**: 已实现

## 上下文

ADR-0022 定义了会签双模式建模。权限校验 `CounterSignWorkflow.validateCounterSignPermission()`
最初采用双模式：

| 模式 | 判定依据 | 加签/减签权限 |
|------|---------|--------------|
| 模式A（偶发会签/伪单例） | 流程变量 `countersignInitiator_<taskDefKey>` 已设置 | 仅会签发起人 |
| 模式B（固定会签） | 变量未设置 | 任意活跃审批人 |

该模型在下游 jw-zhyg-api 实际使用中出现功能死锁（issue #70）：

1. 流程进入会签节点，初始仅 1 名发起人 admin（伪单例）
2. admin 发起会签，加签 B、C、D
3. admin 的子任务被 complete（发起人不投票），admin 待办消失
4. B、C、D 获得待办，进入会签投票

此时前端"加签"按钮对所有活跃审批人可见（`isCanApproval` 仅按活跃审批人过滤），
但后端模式A只认会签发起人。结果是：

- 发起人 admin 有权限但无入口（待办已消失）
- 参与人 B/C/D 有入口但无权限（非发起人被拒）

加签功能整体不可用。

## 决策

将模式A的加签/减签权限从"仅会签发起人"放宽为"**会签发起人 OR 当前节点活跃审批人**"，
与模式B及主流平台（钉钉/飞书均为"当前审批人可加签"）保持一致。

### 减签同步放宽

`validateCounterSignPermission` 为加签/减签共享方法，无法对单一操作差异化放行，
因此减签随加签一并放宽。jw-zhyg-api 业务层已禁用减签（ADR-0004），引擎层放宽
不构成实际风险。

## 后果

- **正面**：
  - 修复模式A加签功能死锁（发起人有权限无入口、参与人有入口无权限）
  - 与主流平台一致，降低接入方认知成本
  - 非活跃审批人仍被拒绝，权限收窄面无安全回退
- **负面**：
  - 模式A从"发起人集中控制"变为"参与人也可加签"，语义变化
  - 模式A下非发起人权限校验多一次活跃审批人查询（与主逻辑查询可复用）
- **风险**：
  - 低：非活跃审批人仍被拒绝，无越权面扩大
