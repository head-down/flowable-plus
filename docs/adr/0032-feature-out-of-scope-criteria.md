# ADR-0032: 范围外功能判据——脱离业务数据即失去价值的功能归业务层

**日期**: 2026-08-11
**状态**: 已接受

## 上下文

2026-08-11 评审候选增强时，对两个"功能性缺失"进行定性：

1. **"我发起的流程列表"**（Phase 3 曾列为下期预留）：按发起人查询流程实例列表。
2. **数据权限详情校验**（`permission-integration-evaluation.md` 记为事实缺失）：对 `getProcessSummary` / `getProcessDiagramStates` 等详情查询做权限过滤。

对二者的共同追问是：**这些能力脱离了业务数据后，是否仍具有独立价值？**

## 决策

新增范围外功能判据：

> **凡脱离业务数据就失去独立价值的功能，归业务层；flowable-plus 只做流程引擎领域内自洽的能力。**

- **框架只提供"答案由流程引擎数据即可独立构成"的能力**。业务字段是锦上添花，靠既有回调机制（如 `queryTodoTasks` 的 `Consumer<TaskQuery>` enhancer、`UserInfoResolver`）由应用填充。
- **若功能的价值高度绑定业务表**（业务单据、部门数据范围、角色），则它是应用层职责。框架不持有业务表，无法替应用判断，做了就是**越界**——既破坏了业务层解耦，又提供"看似安全实则无用"的伪保障。

### 本判据与既有 ADR 的关系

- **ADR-0010**（门面纯聚合）：编排职责归业务层——本判据是其"业务层职责"边界的正向表述（从"业务层该做什么"补上"框架不该做什么"）。
- **ADR-0015**（公开 API 准入）：禁止裸透传——本判据处理"带了增值但增值依赖业务数据"的提案。两者共同构成功能准入的双门：**无增值 → 拒（0015）；有增值但依赖业务数据 → 拒（0032）**。

### 案例应用

| 提案 | 结论 | 判据应用 |
|------|------|----------|
| 待办/已办列表 | ✅ 框架提供 | 答案由流程引擎数据独立构成（谁待办、流程到哪），业务字段靠回调拼接 |
| **"我发起的流程列表"** | ❌ 业务层 | 剥离业务数据后只剩 instanceId+状态，无前端可读性；其价值实质是"业务单据列表"，JOIN 业务表只有业务层能做 |
| **数据权限详情校验** | ❌ 应用层 | 详情可见性取决于业务规则（单据所属范围），框架只能拦"instanceId 不存在"这类技术条件，拦不了业务可见性 |
| 流程表单渲染 / 业务台账导出 | ❌ 业务层 | 同上，价值绑定业务数据 |

### 权限职责三层边界（用于澄清"权限缺失"类提案）

| 层级 | 负责方 | 理由 |
|------|--------|------|
| 操作权限（同意/驳回/撤回/会签） | 框架（`TaskValidation`） | 操作由框架执行、有状态副作用，框架必须自防越权 |
| 列表过滤（待办/已办能查哪些） | 框架提供回调，应用填规则 | 列表是数据集合，应用通过 enhancer 注入部门/角色过滤 |
| 详情可见性（某 instanceId 能否看） | **应用** | 只读无副作用，应用在自己的 Service 入口拦截成本最低、语义最准 |

## 备选方案

- **做"我发起的流程列表"（被否决）**：技术上可行（`queryDoneTasksPrecise` 同款 Native SQL 分页模式可复用），但产出是脱离业务数据即无可读性的残缺列表，诱导业务层绕开回调硬拼，破坏解耦。
- **框架内建数据权限模型（被否决）**：需绑定 RBAC/部门/数据范围等具体模型，违背"不持有业务表、不绑定具体模型"的框架定位。

## 后果

- **正面**：范围边界闭合，未来类似提案（我发起的、表单渲染、台账导出、详情权限）可用一句话判掉，避免重复评审。
- **负面 / 风险**：部分调用方可能期望框架提供"列表带业务字段"的一站式查询，需在文档中明确"业务字段由回调/应用填充"的既有模式。
- 本判据不改变既有功能范围；已交付能力（待办/已办、批量补充、轨迹等）均符合。
