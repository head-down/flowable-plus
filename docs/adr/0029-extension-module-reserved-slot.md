# ADR-0029: flowable-plus-extension 定位为储备位（reserved slot）

**日期**: 2026-08-11
**状态**: 已接受

## 上下文

`flowable-plus-extension` 模块自项目初始化（`35f5a3b`）起即为空壳：仅有
`pom.xml` + `package-info.java`。`package-info` 宣称将包含「多实例处理、高级审批
模式」等高级功能，但：

- 多实例处理（会签投票、加签/减签、委派）已在 `flowable-plus-core` 的
  `CounterSignWorkflow` + `CounterSignOperations` 完整实现；
- 高级审批模式（会签回退策略族、审批轨迹、权限校验）同样已在 core 落地。

即空壳的**所有宣称能力均已由 core 承担**，该宣称构成误导探索者的「假承诺」
（架构审查 2026-08-10 Card F 定性）。

对处置路径展开讨论后（2026-08-11），否决了「直接删除」与「立即填充功能」两个
方向，选择保留模块并明确其边界：

- **不删除**：保留初始设计时预留扩展位的连续性；重建成本虽低（单个 pom），
  但已有候选能力存在真实需求迹象，删除后再建是重复往返。
- **不立即填充**：当前没有任何功能「确定需要但 core 不方便承载」，
  为假设需求提前引入依赖违背项目一贯的「不过度设计」原则。

## 决策

1. **定位**：`flowable-plus-extension` 是「储备位」模块，不是功能模块。
   它是一个有明确边界、当前无内容的模块，等待具备下列判据的功能入住。

2. **填充判据（必须满足其一）**：
   - **依赖隔离**：功能必须引入 core 未引入的依赖（重型或可选的，如 POI、
     Redis client、第三方 SDK），且该依赖不应污染 core 的轻依赖定位；
   - **真正可选的领域能力**：功能是可选的领域扩展，core 承载会模糊核心职责
     （如某种审批模式、某种外部渠道集成）。

3. **禁止项**：
   - **禁止薄壳包装 core 已有功能**（如「会签再包一层」）。core 已实现的能力
     在 core 内增强（更好的默认值、更浅的使用入口），不得在 extension 复制
     入口制造双轨；
   - **禁止「最佳实践集合」类无行为内容**。使用方式归 `flowable-plus-examples`
     示例模块，设计理由归 ADR / CONTEXT.md，不以代码模块形态承载。

4. **package-info 更新**：`package-info.java` 删除「多实例处理、高级审批模式」
   假承诺，改述为储备位定位并指向本 ADR。

5. **已知触发候选**（真实需求出现时按判据评估，不预先实现）：
   - 审批历史导出（`ApprovalRecordVO` → Excel/PDF，引入 POI/iText）
   - 分布式 BPMN 模型缓存（core 的 `BpmnModelCache` 为进程内缓存，
     集群场景可扩展 Redis 实现）
   - IM 审批渠道集成（钉钉/企业微信审批、消息通知，引入对应 SDK）

## 备选方案

- **删除 extension（被否决）**：架构审查 Card F 的立场。否决理由：空壳
  不承担复杂性，删除本身不产生收益转移；但保留设计预留的连续性，且候选能力
  存在真实需求迹象，删除后再建是重复往返。Card F 的核心诉求（消除假承诺）
  通过「package-info 重述 + 边界明文化」同等达成。
- **立即填充一个候选功能（被否决）**：为尚不确定的需求提前引入依赖，
  违背「不为假设的需求设计」原则；且首个填充物若选择「会签包装」将制造
  双轨，与 ADR-0010/0015 的收敛方向相悖。

## 后果

- **正面**：
  - 消除「这里有什么」的假承诺，探索者不再被误导
  - 填充判据与禁止项明文化，未来填充决策有据可依
  - 与 Card F 的核心诉求一致（假承诺消除），同时保留设计预留
- **负面 / 风险**：
  - 模块保持空壳，每次架构审查仍需解释「为什么有个空模块」——由本 ADR
    提供单一解释来源
  - 判据可能被未来维护者误读为「任何带依赖的功能都应进 extension」——
    判据是必要条件而非充分条件，入住仍需按 ADR 流程评估
